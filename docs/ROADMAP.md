## 2. 目標アーキテクチャ

**方針：今の「Core（純C#のルール）＋薄い表示層」の構造を維持して伸ばす。** 実際に動き、テストされ、ブラウザ版とUnity版で共有できているため。新しい設計パターン（ECS、Job System、サーバー同期）は、計測で必要性が分かってから導入する。

```
                 ┌──────────────── 表示層（差し替え可能） ────────────────┐
                 │  Web（Three.js）   Unity（URP）   CLI（検証・計測）   │
                 │  カメラ／入力／UI／描画。ルールは持たない            │
                 └───────────────▲─────────────────┬───────────────────┘
                                 │ 読み取り（スナップショット）│ Command(実行者, 内容)
┌────────────────────────────────┴─────────────────▼──────────────────────────┐
│ Core                                                                         │
│  Session      実行者（世界創造者／住民#id）と権限の確認                        │
│  World        地形・建物・道路・内装定義・被災状態                             │
│  People       住民（属性・予定・能力・人間関係）、操作中の人物（アバター）       │
│  Economy      企業・市場・台帳・家賃（予定）                                   │
│  Transport    道路網・経路・交通量（将来：鉄道・公共交通）                      │
│  Civic        市の政策・研究（将来：国家・外交）                               │
│  Environment  天候・汚染・災害（将来：生態系・地質）                            │
│  Simulation   時計・システム実行（詳細度の切替：注目地域は個別、遠方は集約）    │
│  Persistence  保存（版番号と移行）・分岐                                       │
│  Content      定義データ（JSON）と検証、将来のMOD                              │
└──────────────────────────────────────────────────────────────────────────────┘
```

| 責務 | 置き場所 | 方針 |
|---|---|---|
| 世界データと地形 | World | 当面は1枚。広域化では「地域（Region）」単位に分割し、地域ごとに地形・建物を持つ |
| 建物・道路・インフラ | World | 内装は建物の種類ごとの定義（JSON）から生成。将来はモジュール式の部材 |
| 住民と人物操作 | People / Session | 操作中の人物も普通の住民。違いは「判断をプレイヤーが行う」点だけ |
| ライフシミュレーション | People | 1日の予定、欲求（空腹・疲労）、行動、能力、人間関係 |
| 企業・製造・経済・物流 | Economy | 既存を維持。家賃・住宅市場は判断事項 D3 |
| 交通 | Transport | 既存の道路網を基盤に、人物の徒歩移動は連続座標で別扱い |
| 技術・政治・外交 | Civic | 都市の政策を国家へ広げる段階で再設計 |
| 環境・災害・生態系 | Environment | 既存を維持し、生態系は粗い格子の個体数モデルから |
| 時間管理 | Simulation | 世界は1時間単位のまま。人物の移動・行動は時間の端数で進め、時刻の進み方（速度）は表示側の設定 |
| UI・カメラ・入力 | 表示層 | 視点（カメラ）と権限（モード）を別の仕組みにする |
| 保存・分岐 | Persistence | 版番号ごとの移行関数、履歴の圧縮（古い期間は週・月単位） |
| 拡張コンテンツ | Content | 定義の追加は可、上書きは不可の原則を維持。読込画面と互換性チェックを追加 |
| マルチプレイ | Session | コマンドに実行者を持たせ、検証をCoreで行う。通信方式は後で選ぶ |

**詳細度の切り替え（遠方の集約）**：人口が数千人を超えた段階で、「注目地域（プレイヤーの近く・選択中の地域）」の住民は個別に、それ以外は年齢・職業ごとの人数（コホート）で計算する。移行時は人数・お金の合計が保たれることをテストで保証する。現在の規模（約1,000人、3.8ms/日）ではまだ不要。

## 5. 保存と拡張性の計画

- **形式**：JSON（版番号つき）を維持。地形などの大きな配列は base64。
- **完全性**：乱数状態・日中の途中集計まで保存し、読込後に元と同じ未来になることをテストで保証（実装済み）。人物の状態（F1）も同じテストに含める。
- **版番号**：`SaveSystem.Version` を上げるたびに、旧版から新版への移行関数を追加し、旧版データの読込テストを残す。
- **歴史分岐**：独立した複製（実装済み）を維持。差分保存・巻き戻しは必須にしない。
- **履歴の肥大化**：直近1年は日単位、それより古い期間は週単位に間引く（F2）。
- **ユーザー制作コンテンツ**：定義JSONの「追加のみ・上書き禁止・相互参照の検証」を維持し、保存データに使用中の定義の一覧（ID）を記録する（F2）。
- **マルチプレイ**：すべての変更をコマンド（実行者つき）で行う原則を守る（F1で実行者を導入）。

## 6. 最初に着手する作業と完了条件

**F1 人生体験モード 第1段階**（設計は [LIFE_MODE.md](LIFE_MODE.md)）。既存機能を壊さない追加として実装する。

完了条件：
1. 住民を選んで、または新しく作って操作できる。
2. 一人称・三人称で歩ける。建物に重なって歩けない。
3. 出入口から建物に入り、内装の設備（ベッド・冷蔵庫・レジ・作業台など）を使える。
4. 時刻・所持金・住居・職業・空腹・疲労を確認できる。
5. 買い物（店の在庫と台帳が実際に動く）、就職・退職・出勤（出勤時間に応じた給料）ができる。
6. 勤務先の倒産で失業する、道路の変更で通勤時間が変わる、など世界と連動する。
7. 保存→読込で人物の状態が維持され、読込後も元と同じ未来になる。
8. 世界創造者の操作は人生体験モードでは受け付けない（Coreで拒否）。視点の切替では権限が変わらない。
9. 既存の89件のテストが変わらず成功し、新しいテストもすべて成功する。

## 7. 判断が必要な事項

下の「仮の決定」で作業を進める。いつでも変更できる。

| # | 判断事項 | 仮の決定（理由） |
|---|---|---|
| D1 | 主に使うクライアントを、Web版とUnity版のどちらにするか | Coreは共通のまま、当面はWeb版を主にする（iPadで遊べ、検証もできるため）。Unity版は、PC環境ができた時点で再開する |
| D2 | 人生体験モードの時間の進み方 | 世界のルールは共通のまま、速度の選択肢に「生活（1時間＝20秒）」を追加し、人生体験モードの既定にする |
| D3 | 家賃・住宅市場を入れるか | F3で導入（経済の均衡を再調整する必要があるため、F1では入れない） |
| D4 | 操作中の人物への例外 | 自動の求職・転職・転居・移住・死亡は行わない（プレイヤーの判断に任せる）。解雇・倒産・被災・加齢・物価は他の住民と同じ |

| D6 | 建物内部の表現 | 第1段階は種類ごとに自動生成した1部屋の内装（JSON定義）。自由な内装編集はF4 |
| D7 | 人物の名前 | 住民IDから決まる日本語の名前を自動生成（保存データを増やさない） |
| D8 | ジャイロ | claude.ai上ではジャイロ（端末の動き）を使う許可がない。使える環境（例：GitHub Pagesでの公開）では動作するように作る。公開するかどうかはご判断ください |
| D9 | 最終的な世界の規模の目標 | 未定。F5の前に、面積（km²）・人口・対象端末を決めたい |
| D10 | 公開リポジトリのままでよいか | 現在は公開リポジトリの `worldsim` ブランチ。専用の非公開リポジトリへ移すかどうか |
