### 1.3 計測から分かった問題

1. **計算量が人口の2乗に近い速さで増える。**
   - 人口が5.7倍になると、1日の処理時間は約36倍になる。
   - 最大の原因は小売（6,830人で1日300ms）。次が交通・人口・財務・物流［確認：プロファイル］。
   - 原因［コード確認］：交通システムが3日ごとに渋滞を反映し、道路網を丸ごと無効化する（`Network.Invalidate`）。そのたびに、建物ごとの経路（ダイクストラ法の木）と、小売の「近くの店」の記録が全部作り直される。
   - 計算量は「住宅の数 × 道路の数」に比例する。**地域分割の前に直す必要があります。**
2. **ブラウザ版は、事前コンパイル（AOT）なしの通訳実行で動いている。**
   - `wasm-tools` が未導入のため［確認：ビルドの警告］。
   - AOTにすれば数倍速くなる見込み［推測］。
3. **町を大きくすると失業率が20%を超える。**
   - 町の生成で、工場などの数が固定のまま、人口だけが増えるため［コード確認：`WorldFactory.BuildTown`］。
   - 規模を変えても同じ因果が保たれるには、生成の割合をそろえる必要があります。
4. **シミュレーションと描画は時間の進め方としては分かれているが、同じスレッドで動いている。**
   - 時間の進め方：固定刻みの蓄積方式［コード確認：`SimulationRunner.Update`］。
   - 1日分の処理は1時間ずつ別のシステムに分散している。それでも重い日には、描画のフレームが詰まる［推測］。

## 3. S5「規模と詳細度」のアーキテクチャ案

### 3.0 基本方針：今の「世界」を、そのまま「1つの地域」にする

今の `WorldState` と各システムは、1枚の地図・1つの都市・1つの「外部」を前提にしています［コード確認］。

これを作り直すのではなく、**今の `WorldState` を「詳細に計算する1地域」として、そのまま使います**。その上に、地域どうしを結ぶ層を足します。

既存の仕組みの中で、そのまま地域間の接続点になるもの：
- **外部との接続**：「外部」の口座、輸出入、転入・転出の移民、`HoursToOutside`。
- **今後の扱い**：「隣の地域・国際市場」へとつながる境界として扱い直します。

すべてのシステム（雇用・物流・小売・人口など）は変更なしで再利用できます［コード確認による推測］。

```
世界地図（Atlas：新規）
 ├─ 地域 Region（ID、地形の概略、都市、河川・海岸・港の有無、詳細度）
 │    ├─ 詳細に計算する地域：今の WorldState（個人・企業・建物・道路、1時間刻み）
 │    └─ 集団で計算する地域：RegionAggregate（新規。年齢・学歴・就業別の人数、産業別の能力、住宅、市の財政）
 ├─ 地域間の接続 RegionLink（道路・のちに鉄道・海路。所要時間・輸送力・運賃）
 ├─ 地域間の市場 WorldMarket（資源ごとの地域間取引。市外の世界は今の「外部」として残す）
 └─ 地域間の移住 Migration（地域の魅力度：求人・家賃・満足度・環境で人が動く）
```

### 3.1 地域分割と地域ID

- **地域ID**
  - `RegionId`（整数、1から）を、地域に属するすべての物の名前空間にする。
  - 建物・住民・企業のIDは地域ごとの番号のまま。地域をまたぐ参照は（地域ID, 番号）の組にする。
- **地域の大きさ**
  - 詳細に計算する地域は、今の地図の大きさ（128〜256マス）を基本にする。
  - 広い世界は「地域を並べる」ことで作る。1枚の巨大な地図にはしない。
  - 理由：1.3節の計算量の問題と、保存・読み込みを地域単位で扱えるようにするため。
- **地形の扱い**
  - 世界地図は粗い格子（例：1マス＝1km）で持つ：高さ・河川・海岸・資源の埋蔵・気候帯。
  - 地域を詳細にするとき、その範囲から今の細かな地形を決定的に生成する。
- **乱数**
  - 地域ごとに独立した乱数の流れにする（世界の種 ＋ 地域ID から作る）。
  - こうすると、ある地域への介入が他の地域の乱数をずらさない。介入実験の雑音も減る。

### 3.2 複数の都市と、地域間の移住・物流・経済

| 流れ | 仕組み | 既存のどれを置き換えるか |
|---|---|---|
| 物流・交易 | 各地域が資源ごとに余り（輸出に回す量）と不足（輸入したい量）を出す。WorldMarket が接続の所要時間・運賃・輸送力で、安い順に割り当てる。足りない分は「外部」から輸入 | 今の「輸出入」は、まず地域間で取引し、残りだけを外部と取引する |
| お金 | 地域ごとに「境界」の口座を持ち、地域間の支払いは帳簿の新しい流れの種類（地域間取引）で記録する。世界全体でお金の総量を検証する | 「外部」の口座を地域ごとの境界に分ける |
| 移住 | 地域の魅力度（求人・家賃・満足度・健康・通勤）の差で人が動く。転出は相手の地域への転入になり、外部へ消えない | 今の移入・移出の式を、地域間の流れの一部にする |
| 原因の記録 | 地域ごとに記録し、地域間の流れには相手の地域IDを残す（例：「B市の求人を求めて転出」） | 原因コードと関係者の欄をそのまま使う |
| 価格 | 地域ごとの価格と、地域間の運賃で決まる鞘（価格差） | 今の市場価格の決め方をそのまま地域ごとに使う |

### 3.3 詳細度の切り替え（プレイヤーの近くは個人、遠方は集団）

- **詳細（Detailed）**
  - 今のシミュレーションそのもの。
  - 対象：プレイヤーが見ている地域、人生体験中の人物がいる地域、その隣（端末の設定で数を決める）。
- **集団（Aggregate）**
  - 人口：地域 × 年齢層（0-17／18-29／30-44／45-64／65+）× 学歴 × 就業状態 ごとの人数、平均貯蓄、平均の健康・満足度。
  - 企業：産業（建物の種類）ごとの数、雇用、生産能力、在庫、資金、平均賃金、利益。
  - そのほか：住宅（戸数・空き・家賃）、市の財政と政策、環境（汚染・電力）。
- **同じ式で計算する**
  - 集団モデルも、消費のかご・生産のレシピ（1人あたり）・賃金の規則・移住の式・税は、詳細モデルと**同じ定義データと同じ式**を使う。
  - 違うのは、個人を足し合わせるか、人数に掛けるかだけ。
  - そのために、式を「個人の関数」と「集団の関数」の両方から呼べる形にしていく（式のデータ化 D と同時に進める）。

### 3.4 切り替えても不整合を起こさない仕組み

**変わらないもの（ずっと保持するもの）**
- 建物・道路・地形は、詳細度にかかわらず常にそのまま保持する。
- 切り替えで変わるのは、人と企業の表し方だけ。

**詳細 → 集団（畳む）**
- 個人を足し合わせて、層ごとの人数・お金の合計・平均にする。人数とお金の合計は、ぴったり一致させる。
- 企業は産業ごとに合計する。建物との対応（どの建物が何の企業か）は残す。

**集団 → 詳細（展開する）**
- 層ごとの人数どおりに個人を作る（地域の乱数で決定的に）。
- お金は合計が一致するように配る。住まいと職場は、建物の定員と企業の雇用の合計に合わせて割り当てる。

**固定の個人**
- 操作中の人物、その家族・知り合い（Relations）、名前のある人物（市長など、将来）。
- これらは集団化せず、地域が集団になっても個人のまま残す。関係・資産・履歴が失われない。

**検証するテスト**
- 往復テスト：詳細→集団→詳細で、人口・労働力・就業者・年齢構成・お金の総量・企業の数と雇用・建物が一致し、固定の個人はIDごと同じになる。
- 長期実行：切り替えを繰り返しながら長く実行しても、お金の総量の検証と WorldValidator が通る。
- 原因の記録：切り替えそのものは原因の記録上「変化なし」として扱い（専用の原因コード）、人口などの分解に混ざらないようにする。

### 3.5 遠方の地域の時間の進め方

- **詳細地域**：今と同じく1時間刻み（日次システムを1時間ずつずらして実行）。
- **集団地域**：1日刻みで、まとめて計算する。
  - 1日分の計算は、詳細地域の「その日の統計の時刻」に合わせ、地域ID順に実行する（決定的）。
  - 端末が重いときは、集団地域だけ7日刻みにする設定も持つ（同じ式で日数分を掛ける）。精度が変わるだけで、規則は変わらない。
- **地域間の交易と移住**：1日1回、全地域の計算が終わったあとにまとめて決済する。
- **高速で進めるとき（16倍以上）**：まず詳細地域の1日の時間を短くする（1.3節の対策）。それでも足りない端末では、詳細地域の数を減らす。

### 3.6 保存・読み込み・歴史分岐との互換性

- **保存v4**
  - `{ atlas, regions: [{ id, lod, detailed: <今のv3の世界データ> | aggregate: {...} }], links, worldMarket, pinned }`
  - v3 は「詳細な1地域だけの世界」として読む（互換性を維持し、テストで確認する）。
- **歴史分岐**：保存を通して丸ごと複製する今の方式のまま使える。地域が増えると複製は重くなる。
  - 対策：分岐時は集団地域を共有し、書き換えたときだけ複製する［推測：S5後半で検討］。
- **再現性**
  - 地域ごとの乱数と、地域ID順の処理で決定性を保つ。
  - 世界のハッシュは、地域ごとのハッシュを順に合成する。
- **保存の大きさ**
  - 詳細地域1つ（約1,200人）で、10年後に約3MB［確認］。集団地域は1つあたり数KBの見込み［推測］。
  - 履歴は直近1年を日単位、それより前を週単位に間引く（ROADMAPの方針を引き継ぐ）。

### 3.7 PC・スマートフォン・タブレットごとの調整

|---|---|---|

| 集団地域の刻み | 1日刻み／7日刻み | 地域間の交易・移住の規則 |

**Unity を再開するときの順序**

## 5. 性能目標案（計測に基づく提案）

### 5.1 時間の予算の考え方

- **16倍速の場合**：ゲーム内1日が0.75秒で進みます（1日24時間 ÷ 毎秒32時間）。1秒のうちシミュレーションに使ってよい時間を約30%とすると、**1日あたり約220ms**が上限です［推測：描画とUIに残りを使う前提］。
- **人生体験中の「生活」速度の場合**：1時間が20秒なので、予算には余裕があります。

### 5.2 端末別の目標（いずれも実機での計測が前提の「提案」です）

| 項目 | PC（ブラウザまたはUnity） | タブレット（iPad、ブラウザ） | スマートフォン（ブラウザ） |
|---|---|---|---|
| 詳細地域の人口 | 合計 20,000人 | 5,000人 | 2,000人 |
| 地域の数（詳細＋集団） | 4＋12 | 2＋6 | 1＋3 |
| 詳細地域の1日の処理時間 | ≤ 50ms（16倍速で余裕） | ≤ 60ms | ≤ 60ms |
| 描画フレームレート | 60fps | 30fps | 30fps（低画質） |
| メモリ | ≤ 1.5GB | ≤ 600MB | ≤ 400MB |
| 保存データ | ≤ 30MB | ≤ 10MB | ≤ 5MB |
| 保存・読込 | ≤ 2秒 | ≤ 3秒 | ≤ 3秒 |
| 長期の安定性 | 20年で人口・失業率が許容範囲内、お金の総量は常に一致 | 同じ | 同じ |
| 再現性 | 同じ保存データ・同じ操作で、ハッシュが完全に一致 | 同じ | 同じ |

### 5.3 根拠と前提

- **ネイティブ**：今は約4,200人で1日129ms［確認］。経路の再計算（1.3節）を直せば、人口に対して1次関数的に増える見込みで、20,000人で約50msと試算しています。
  - 試算の根拠：既定の町の約6〜12msを人口比で伸ばした値［推測］。
- **ブラウザ**：今は約1,200人で1日75ms［確認］。AOTで数倍速くなる見込みです。iPadでは、まずAOTとこの改善を組み合わせて5,000人を目指します［推測］。
- **実機**：iPadとスマホは未計測です。最初のタスク（7章）で、端末ごとに計測ページを開けば同じ形式の結果が出るようにし、目標値をそこで見直します。
