## 0. 結論（要約）

1. **技術構成は書き直さず、そのまま伸ばすことを推奨します。** 理由は以下です（詳細は3章）。
   - 決定的で検証可能なC#の本体（104件のテスト、10年連続実行、保存→読込で同じ未来）が、すでに「質で超える」ための土台として機能しています［確認］。
   - 1日あたり約4msと軽く、大規模化の余地があります［確認］。
2. **最大の不足は「規模」ではなく、次の3点です。**
   - **説明可能性**：なぜ起きたかを追跡できない。
   - **自律性**：企業・自治体が目的を持って判断しない。
   - **閉じていない因果の輪**：地価・健康・建設業・家賃などが、計算されても他に効かない、または存在しない。
3. **介入実験で、因果はおおむね成立していることを確認しました［確認］。** ただし説明できない結果やバグも見つかりました（1.3節）。
4. **最初の段階（S1）は「因果の検証と説明」です。**
   - 介入実験を自動テストにする。
   - 主要指標の変化を原因別に分解して示す「なぜ？」機能を作る。
   - 見つかった不具合を直す。
   - 新機能を増やす前に、今ある因果を確かなものにします。

### 1.3 介入実験（因果プローブ）の結果［確認］

**方法**
- 種1の町を60日進めて保存する。
- それを読み込み、介入を1つだけ加えて90日進める。
- 最後の14日の平均を、介入なしの基準と比べる。

| 介入 | 主な結果（基準との差） | 評価 |
|---|---|---|
| 所得税 0.25→0.40 | 市の資金 +21%、小売 −2.7%、輸入 −3.9% | 妥当 |
| 法人税 0.60 | 市の資金 +10%、失業 +4.5%、営業企業 −1% | 妥当 |
| 産業補助 2万円/人 | 失業 −19%、工業製品 +131%、市の資金 −85%、汚染 +17% | 妥当（効果が強すぎる可能性） |
| 失業手当 0 | 市の資金 +9%、小売 −3.8%、満足度 −1.5% | 妥当 |
| 年金 0 | 満足度 −8%、食品生産 −29%、**電力供給 −29%**、企業利益 −107% | 電力が下がる経路が説明できない（要調査） |
| 電気料金 100円 | **食品生産 −100%**、失業 +24%、企業利益 +79% | 崖のような急変。理由の説明ができない（要調査） |
| 発電所をすべて撤去 | 全生産 −100%、失業 +76%、満足度 −37% | 妥当 |
| 商店をすべて撤去 | 小売 −86%、人口 −18%、**輸入 −100%** | 輸入が小売にしか使われていない（設計上の偏り） |
| 食品工場を撤去 | 食品生産 −100%、**輸入 +24%** で補われる | 妥当 |
| 研究所・学校を撤去 | 失業 +8%、工業製品 −8%（学歴要件） | 妥当 |
| 遠方に集合住宅10棟 | 市の資金 −50%、**人口 ±0%** | 道路がなく住めない可能性［推測］。手掛かりを示す機能がない |
| 地震 M7.5 | 市の資金 −50%、**失業 −30%**、**人口 +3%**、輸出 +45% | 直感に反する。原因不明［未確認］ |

**分かったこと**
- 政策・建物・災害の変更は、税収・雇用・小売・生産・満足度・人口へ実際に波及しています。**飾りの機能ではありません**［確認］。
- 一方で、**なぜそうなったかをゲーム内でも開発者側でも追跡できません。** 既存の「原因診断」は約12個の固定ルールで、最新の状態を見るだけです［コード確認］。
- 基準の町は、この期間の失業率が約20%でした［確認］。以前の文書の「約10%」は別の期間・条件の値です。

### 1.4 見つかった不具合・切れた因果［コード確認］

1. **火力発電所が汚染を出していない。** 電力（4時）が発電量を記録しても、生産（6時）が全企業の生産量を0に戻し、汚染（13時）はその0を読みます。
   - 結果：発電所の汚染値80も、排煙装置の技術も効いていません（導入費用だけ支払っている）。
2. **地価は表示専用。** 住む場所の選び方にも価格にも使われていません（地価という説明と矛盾）。
3. **健康の概念がない。** 汚染は満足度を下げますが、死亡率は年齢だけで決まります。
4. **温暖化は土の乾きにしか効かず、影響もごく小さい**（ほぼ飾り）。
5. **サービス（オフィス）は企業間取引・輸出の対象外。** 過剰在庫→赤字→解雇の循環が起きやすい［推測］。
6. **復旧費・建設費は市外へ支払われる。** 地元に建設業がないため、災害復興が地元の雇用を生みません。
7. **新しい企業はプレイヤーが建てたときだけ生まれる。** 企業が自分で出店・拡張・移転・値付けをすることはありません。自治体は判断する主体として存在しません。

## 3. 推奨するシステム構成と理由

### 3.1 維持するもの（理由つき）

| 方針 | 理由 |
|---|---|
| 純C#のシミュレーション本体＋薄い表示層（Web／Unity） | 表示から独立して自動テストでき、同じ世界を俯瞰・一人称・CLIで共有できる［確認］ |
| 決定的な固定時間刻みの実行・保存した乱数状態 | 歴史分岐・比較・再現・将来のマルチプレイの前提になる［確認］ |
| お金を整数円の帳簿で移動し、総量を検証 | 経済の一貫性を自動で保証できる［確認］ |
| コマンド経由の変更と実行者（権限）の確認 | プレイヤー・AI・他プレイヤーを同じ経路で扱える［確認］ |

### 3.2 追加する仕組み（目標から逆算）

| 仕組み | 内容 | 目的（観点） |
|---|---|---|
| **A 原因の記録** | 雇用・解雇・倒産・価格変更・移住などの変化に、原因の種類と関係者を付けて残す（例：「解雇／理由＝電力不足／企業#12」）。帳簿の資金の流れには、すでに種類がある | 説明可能性 |
| **B 指標の分解** | 「失業率がなぜ変わったか」を、記録Aから原因別の寄与に分けて示す（例：倒産+3%、電力不足+2%、移住−1%） | 説明可能性・分岐比較 |
| **C 判断する主体の枠組み** | 企業・自治体・（将来）国家・研究機関に共通の「目的・観測・選択肢・制約・判断」の形を与える。判断は理由つきで記録する（Aへ） | 自律性・説明可能性 |
| **D 式と係数のデータ化** | 満足度の重み・移住・価格の幅・消費のかご、などをJSONの「ルール定義」へ移す | 拡張性・MOD |
| **E 詳細度の切替（LOD）** | プレイヤーの近くと注目中の地域は個人単位、遠方は集団（年齢・職業別の人数）で計算する。両者の行き来を定義する | 実用的な性能・規模 |
| **F 地域（チャンク）分割** | 世界を地域に分け、地域ごとに電力・市場・交通をまとめ、地域間を結ぶ | 規模・複数都市・国家 |
| **G 変更の記録と再生** | すべてのコマンドを時刻つきで記録し、再生できるようにする | 分岐・不具合再現・マルチ |

### 3.3 層の構成（目標）

```
表示層（Web／Unity／CLI）  … 描画・入力・UI。ルールを持たない
  ↓ コマンド（実行者つき）／問い合わせ
セッション層        … モード、実行者、コマンド記録（G）、分岐管理
  ↓
シミュレーション層  … 固定刻みの実行器、システム群、主体の判断（C）、LOD（E）
  ↓ 読み書き
世界データ層        … 地形・地域（F）・建物・道路・住民・企業・帳簿・環境・原因記録（A）
  ↑
内容データ層        … 建物・資源・技術・内装・ルール定義（D）・MOD
分析層             … 統計・指標の分解（B）・予測・比較（シミュレーションの外から読むだけ）
```

## 4. 主要システム間のデータと因果関係［コード確認］

```
               ┌──────── 政策（税・補助・年金・手当・電気料金・防災・復旧） ────────┐
               ↓                                                                ↓
 天候 → 土壌水分 → 農業生産      電力供給 → 生産効率・研究・満足度      市の財政 ← 税
   ↑                              ↑ 発電所の人手・損傷                     ↓ 給付
 温暖化(微小) ← 排出 ← 生産量 → 汚染 → 満足度・住む場所・植生          住民の所得
                                   ↑                                       ↓
 原料 → 中間財 → 製品（企業間取引・運賃・輸出入）→ 在庫 → 小売 → 消費の充足 → 満足度
     ↑ 価格（需給で±2%/日）            ↑ 雇用（利益・在庫・人手不足）  ↑ 賃金
 道路網 → 交通量 → 渋滞(3日ごと) → 移動時間 → 通勤・運賃・店選び・転居・仕事選び
 災害 → 建物・道路の損傷 → 生産・住める家・満足度 → 復旧（予算・消防）
 研究 → 技術 → 生産性・必要人員・電力・汚染・運賃・耐災害
 満足度・求人・空き家・失業率 → 移入／移出 → 人口 → 需要と労働力
```

### 4.1 輪になっている主な因果（強化・抑制）

| 輪 | 種類 | 内容 |
|---|---|---|
| R1 | 強化 | 雇用 → 所得 → 消費 → 売上 → 雇用 |
| B1 | 抑制 | 需要増 → 価格上昇 → 購入量減 |
| B2 | 抑制 | 交通集中 → 渋滞 → 迂回・転居 → 交通分散 |
| B3 | 抑制 | 失業増 → 賃金低下 → 企業利益 → 雇用 |
| B4 | 抑制 | 人手不足 → 賃上げ → 移入 |
| R2 | 強化 | 汚染 → 植生減 → 吸収減 → 汚染 |

### 4.2 欠けている因果（1.4節と重複するものを含む）

| 欠けている輪 | 影響 |
|---|---|
| 地価 → 家賃 → 住む場所・生活費 | 住宅市場がない |
| 汚染 → 健康 → 死亡・労働 | 環境が命に効かない |
| 建設・復旧 → 地元の建設業の雇用 | 公共事業が地元経済を動かさない |
| 企業の利益 → 出店・拡張・撤退 | 経済が自分から成長しない |
| 市の財政 → 自治体の判断（増税・投資） | 政策が動くのはプレイヤーが変えたときだけ |
| 地域ごとの電力・市場 | 規模を広げると一律の計算が成り立たない |

## 6. PC・スマートフォン・タブレットへの対応方針

| 項目 | 方針 |
|---|---|

| 性能目標 | 端末ごとの目標（例：iPadで1万人・30fps）を D9 の判断後に決め、CLI・ブラウザの自動計測で守る |

## 7. 最初に実装すべき具体的なタスク（S1）と完了条件

### タスク S1-1 因果プローブを自動テストにする
介入→期待する向きの変化を、自動テストとして固定します。例：
- 所得税を上げる → 市の資金が増え、小売が減る
- 発電所を撤去する → 生産が下がり、失業が増える

あわせて、CLIに `--probe` を追加し、1.3節の表を出力できるようにします。

**完了条件**
- 10件以上の介入テストが成功する。
- 同じ実行を2回して、結果の差が0。

### タスク S1-2 不具合の修正
- 発電所の汚染（1.4-1）を直す。
- 原因が不明な結果（電気料金の崖、年金と電力、地震後の失業減、遠方の住宅）を調べる。
  - 調べた結果は「不具合として修正」か「理由を文書化」のどちらかにする。

**完了条件**
- 発電量に比例した汚染が出ることをテストで確認できる。
- 不明な4項目すべてに結論が書かれている。

### タスク S1-3 原因の記録（A）
雇用・解雇・倒産・再開・移入・移出・転居・価格変更に、次を記録します。
- 原因コード（例：利益悪化／在庫過多／電力不足／被災／通勤が長すぎる）
- 関係する主体
- 日付

保存の方針：
- 直近90日分を保存対象にし、古い分は日ごとの集計に圧縮する。
- 保存形式を v3 に上げる（v1・v2 も読める）。

**完了条件**
- 記録の合計が統計と一致する（例：解雇の件数）。
- 10年後の保存サイズの増加が +20% 以内。

### タスク S1-4 指標の分解（B）と「なぜ？」UI
- **分解する指標**：失業率・人口・市の資金・物価（食品・製品）の4つ。
  - 指定した期間の変化を、原因別の寄与に分けて示す。
- **UI**：Web版の上部の指標を押すと、「なぜ？」パネルに分解結果が出る。
  - 企業・建物を選ぶと、その場所へ移動する。
- **分岐との連携**：分岐比較にも「差が生まれた主な原因」を出す。

**完了条件**
- 分解した寄与の合計が実際の変化の90%以上を説明する（テスト）。
- ブラウザ自動テストで表示を確認する。

### S1 全体の完了条件
- 既存104件と新しいテストがすべて成功する。
- 10年連続実行で整合性の問題がない。
- 保存→読込で同じ未来になる。
- ブラウザ自動テストでエラーがない。
- 性能の低下が1日あたり +20% 以内。

## 8. 将来の拡張を妨げないために、初期から設計しておく要素

1. **実行者と原因を、すべての変更に付ける。**
   - 誰が（プレイヤー／企業／自治体／災害）、なぜ変えたか。
   - 説明・マルチプレイ・AIの判断の土台になります（実行者は実装済み、原因はS1）。
2. **主体の判断は「目的・観測・選択肢・制約」の共通形にする。**
   - 規則の企業も将来の学習する国家も、同じ形で差し替えられるようにします。
3. **個人と集団の両方で表せるデータにする。**
   - 住民・企業は、将来「集団（人数・平均）」に畳めるようにします。
   - 個人にしかない値（名前・関係）は別に持ちます。
4. **地域IDを早めに入れる。**
   - 今は地域が1つでも、電力・市場・統計を「地域ごと」の形にしておくと、S5の書き直しが小さくなります。
5. **式・係数をデータへ移す。**
   - 新しい式は最初からJSONのルール定義にし、MODで差し替え可能にします。
6. **保存形式の版と移行処理を必ず用意する**（v1→v2で実施済み）。
7. **決定性を守る規則を明文化し、テストで検査する。**
   - 並び順の固定、乱数は世界の乱数のみ、浮動小数の累積誤差に注意。
8. **単位を明記する。**
   - 円（整数）、時間（tick＝1時間）、距離（m）、資源の単位。
   - 混同を防ぎ、表示の換算を一箇所にまとめます。
9. **分析はシミュレーションの外から読むだけにする。**
   - 表示や分析が結果を変えない構造を維持します。
